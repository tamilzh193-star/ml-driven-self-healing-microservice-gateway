📚 1. Executive Project Overview

Background motivation, problem formulation, dissertation objectives, and architectural methodology.

⚠ Problem Formulation

Modern cloud systems adopt distributed microservices communicating across asynchronous and synchronous network channels. These architectures suffer from:

  • Silent Performance Degradation: Progressive memory leaks and thread pool stalls that pass binary UP/DOWN health checks.
  • Cascading Failure Storms: When downstream services slow down, upstream callers exhaust thread pools and fail symmetrically.
  • Alert Fatigue & Delayed MTTR: Static threshold monitors require manual on-call engineer intervention, leading to prolonged recovery times.

🎯 Project Objectives

To design, implement, and rigorously verify an autonomous, closed-loop resilience gateway that:

  • Continuously ingests multivariate telemetry (CPU, Memory, Latency, Error Rate, Request Rate) from microservices.
  • Executes real-time unsupervised anomaly detection using an Isolation Forest ML model.
  • Suppresses transient noise via Severity-Weighted Evidence Accumulation (SWEA).
  • Pinpoints causal failure signatures via Leave-One-Feature-Out (LOFO) attribution.
  • Suppresses victim remediations under cascading DAG dependency failures.
  • Executes autonomous recovery actions guided by Contextual Thompson Sampling with database persistence.

🧠 Self-Healing Pipeline

The proposed architecture introduces a closed feedback loop combining:

  • Ingestion: 5-second interval multivariate telemetry aggregation.
  • Inference: Isolation Forest boundary scoring (θ = -0.5140).
  • Confirmation: Temporal SWEA accumulator requiring sustained anomaly proof.
  • Remediation: Multi-tier escalation ($L_1$ Rate Limit, $L_2$ Traffic Redirection, $L_3$ Container Restart).
  • Verification: Two-stage health and business endpoint synthetic transaction audit.
Academic Scope & Limitation Notice: This project is an applied Master of Computer Applications (MCA) dissertation engineering prototype. The machine learning model was trained and evaluated on synthetic telemetry collected in a controlled test harness. Results reflect architectural design verification under synthetic workloads rather than multi-year enterprise production operations.

⚠ Essential Academic & Model Limitations

  • Held-Out vs. Production: These figures reflect performance on a disjoint 308-row held-out test file (dataset/test_heldout.csv), NOT continuous live production accuracy.
  • Synthetic Telemetry Session: The dataset was collected during a single multi-stage synthetic telemetry session. It verifies detection capability under injected fault patterns, but does not prove generalization across disparate real-world enterprise architectures.
  • Fault Samples in Training: The training dataset (dataset/train_clean.csv) contains 12 fault rows (800 rows total) due to boundary transitions during data capture; it is not purely pristine data.
  • Why Accuracy Alone is Misleading: In anomaly detection datasets, normal operational records vastly outnumber fault records (e.g. 263 normal vs. 45 fault rows in test data). A trivial model that always predicts "Normal" would achieve ~85% accuracy while failing to detect any outages. Hence, Recall (91.11%) and FPR (4.94%) are the governing performance criteria.
  • False Positives vs. False Negatives: A False Positive causes unnecessary throttling or container restarts; a False Negative allows an unmitigated outage to propagate. The calibrated threshold ($\theta = -0.5140$) enforces FPR $\le 5\%$ to prevent false restarts while maintaining $> 90\%$ recall.

🛡 4. Self-Healing Implementation Components

Concrete software mechanisms implemented in the Java gateway and Python ML microservice.

1. Severity-Weighted Evidence Accumulation (SWEA)

Class: AnomalyConfirmationService.java

Purpose: Replaces naive event counting with a recursive evidence accumulator $E_t = \lambda_a E_{t-1} + g(s_t)$. Severe anomalies ($s_t < -0.30$) accelerate evidence accumulation to trigger confirmation in 2 observation cycles ($\sim 9.4$s vs. $15$s standard window), while transient jitter decays exponentially.

Verified (Unit Tests: SweaConfirmationTest)

2. Leave-One-Feature-Out (LOFO) Attribution

Module: ml-service/app.py

Purpose: Resolves the "black-box" dilemma of unsupervised Isolation Forests by replacing each feature with its baseline median, measuring the score delta, and outputting normalized percentage contributions mapping to failure signatures (LATENCY_SPIKE, MEMORY_LEAK, ERROR_BURST, CPU_SATURATION).

Verified (Unit Tests: test_attribution.py)

3. Contextual Thompson Sampling

Class: HealingStrategySelector.java

Purpose: Models remediation success probabilities as Beta distributions $\text{Beta}(\alpha, \beta)$ conditioned on context keys (e.g. latency:severe). Uses an exact Marsaglia-Tsang Gamma generator to sample actions, balancing exploration and exploitation.

Verified (Unit Tests: OutcomeLearningPolicyTest)

4. Topology DAG Root-Cause Suppression

Class: ServiceTopologyService.java

Purpose: Evaluates service call directed graphs. When an upstream caller (e.g. order-service) exhibits latency symptoms because downstream payment-service is degraded, the engine suppresses remediation on the caller and targets the root cause directly.

Verified (Unit Tests: RootCauseLocalizationTest)

5. Multi-Tier Escalation Ladder

Classes: RemediationExecutionService.java, DockerRestartExecutor.java

Purpose: Implements a progressive mitigation ladder: Tier 1 ($L_1$) Dynamic Rate-Limiting, Tier 2 ($L_2$) Fail-Fast Traffic Redirection, and Tier 3 ($L_3$) Genuine Container Restart via mounted Docker socket with soft-reset fallback.

Verified (Unit & Docker Integration Tests)

6. Policy Statistics Relational Persistence

Classes: DatabasePersistenceService.java, HealingStrategySelector.java

Purpose: Persists updated Beta distribution parameters ($\alpha, \beta, \text{successes}, \text{failures}$) to MySQL table policy_stats. Validates records at gateway startup, restoring learned policies across restarts.

Verified (Unit Tests: PolicyPersistenceTest)

🔄 5. Autonomous Recovery Execution Flow

The 8-stage closed-loop operational lifecycle from telemetry ingestion to relational outcome learning.

1

Scheduled Telemetry Polling (Every 5 Seconds)

Gateway's TelemetryCollectorService polls Spring Boot Actuator endpoints (/actuator/metrics, /actuator/health) across all registered services, aggregating 5 normalized features: CPU, Memory, Latency, Error Rate, and Request Rate.

2

Flask Isolation Forest Inference & Attribution

Gateway posts telemetry vectors to :5000/predict. The ML daemon computes the Isolation Forest score ($s_t$) and applies LOFO margin decomposition to compute percentage attribution shares and determine the failure signature.

3

Severity-Weighted Evidence Accumulation (SWEA)

Gateway updates evidence $E_t = \lambda_a E_{t-1} + g(s_t)$. If $E_t \ge \theta = 3.0$, the anomaly is confirmed. Severe anomalies confirm in 2 cycles; transient jitter rapidly decays, preventing flapping.

4

Topology DAG Root-Cause Evaluation

Before executing healing, ServiceTopologyService checks if any downstream dependency is confirmed anomalous. If the caller exhibits external latency symptoms, remediation on the caller is suppressed (SUPPRESSED_TOPOLOGY).

5

Contextual Thompson Sampling Strategy Selection

The selector samples Beta variates $\theta_{C,a} \sim \text{Beta}(\alpha, \beta)$ for candidate actions ($L_1, L_2, L_3$) conditioned on context key. The action maximizing expected utility is chosen; sustained failures automatically escalate.

6

Remediation Execution

Gateway activates dynamic route rate-limiting, traffic fallback redirection (HTTP 503 retry-after), or invokes container restart via Docker socket. Cooldown timers protect against rapid restart loops.

7

Closed-Loop Health Verification Probe

Following action execution and a cooldown delay, the gateway executes active probes: Actuator liveness and synthetic business transaction requests (e.g. GET /orders). Status is confirmed RECOVERED only upon verified HTTP 200 responses.

8

Outcome Audit & Policy Statistics Persistence

If verified healthy, $\alpha$ is incremented; if unrecovered, $\beta$ is incremented. Posteriors are persisted to MySQL table policy_stats, and an immutable record is logged in healing_audit_logs.

🚀 6. Execution & Viva Demonstration Guide

Step-by-step instructions for running the cluster and conducting a live self-healing evaluation.

🔑 Local Admin Key Setup

Administrative actions require X-Admin-Key authentication. For local demonstrations, the key defaults to a demo placeholder or is set via environment variable:

set ADMIN_AUTH_ENABLED=true set ADMIN_API_KEY=demo-admin-secret-change-me

In the Operations Dashboard, click the Admin Key button to view or update your key stored in local session.

💻 Starting the Cluster

Option A (Standalone Bat Script):

run_all.bat

Option B (Docker Compose):

docker compose up -d

Access the Operations Dashboard at: http://localhost:8080/dashboard

🎓 3-Minute Viva Demonstration Script

  • 1. Baseline Health: Open Dashboard. Show all 3 microservices green, ML service online, and calibrated threshold $\theta = -0.5140$.
  • 2. Inject Latency: In the Chaos Console, click "Slow Latency (+1.6s)" on payment-service.
  • 3. Observe SWEA Confirmation: Show status transition from HEALTHY → SUSPECT → CONFIRMED_ANOMALY.
  • 4. Autonomous Healing: Observe Gateway trigger TRAFFIC_REDIRECTION or RESTART.
  • 5. Verified Recovery: Watch the audit trail transition to RECOVERED, restoring latency to $< 25$ms.
